# ADR-0004: Build the Content Security Policy from hashes of the rendered HTML

**Status:** Accepted
**Date:** 2026-10-02
**Deciders:** BogDev maintainer

## Context

The site sent no security headers. Articles render rich text from Strapi into HTML, sanitized with `sanitize-html`; a Content Security Policy is the second line of defence if sanitizing ever misses something. Every page has three executable inline scripts: the theme script that avoids a flash of the wrong theme, Nuxt's `importmap` and `window.__NUXT__.config`. The importmap changes with every build and the config with every environment. Pages are cached with ISR ([ADR-0001](0001-isr-without-cdn.md)), so per-request values cannot appear in cached HTML.

## Decision

A Nitro plugin (`server/plugins/contentSecurityPolicy.ts`) hooks `render:html`, takes the SHA-256 of every executable inline script in the final HTML and sends a policy whose `script-src` is `'self'` plus those hashes, without `'unsafe-inline'`. The header is cached together with the HTML, so it always matches it. Images are limited to the site, Strapi and the media host; frames to YouTube and Vimeo, the same players the sanitizer allows; `frame-ancestors`, `object-src`, `base-uri` and `form-action` are locked down. `style-src` keeps `'unsafe-inline'` for Vue style bindings and Mermaid. Fixed headers (HSTS, `nosniff`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy`, COOP) go on every response through a route rule. The policy applies in production only.

## Options considered

### A. Hashes computed from the rendered HTML (chosen)
| Dimension | Assessment |
| --- | --- |
| Complexity | Low: one hook and a pure helper |
| Strength | No inline script runs unless it is exactly one of the page's own |
| Caching | Compatible with ISR: header and HTML are cached together |
| Maintenance | None when scripts change between builds or environments |

### B. Nonces
**Pros:** the standard strict CSP. **Cons:** a nonce must change per response, which a cached page cannot do; it would mean giving up ISR.

### C. `script-src 'self' 'unsafe-inline'`
**Pros:** trivial. **Cons:** allows any injected inline script, which is the main thing a CSP is for.

### D. Hashes fixed at build time in `nuxt.config.ts`
**Pros:** a static header. **Cons:** `window.__NUXT__.config` depends on runtime environment variables, so the hash is unknown at build time and would break whenever the configuration changes.

## Trade-offs

Inline styles stay allowed: blocking them would break Vue bindings and Mermaid diagrams, and style injection is far less dangerous than script injection. The policy is not applied in development, where Vite injects its own scripts, so CSP problems only show in production builds.

## Consequences

- A new image, embed or script domain must be added in `contentSecurityPolicy()` and, for embeds, in the `sanitize-html` options together ([security.md](../security.md)).
- Integration tests check that the hashes in the header match the inline scripts of each page, also when the page is served from the ISR cache.
- Verify a change to the policy in a production build in a browser, listening for `securitypolicyviolation`.

**Amendment (2026-10-07, #244):** `media-src` is `'self'` plus the origins of `img-src` (Strapi and the media host), so the `<video>` of a page section can play uploaded files; videos never autoplay. Page media is limited to `/uploads/` paths and those origins on both the server schema and the frontend.

**Amendment (2026-10-07, #243): static builds.** A static site has no response to attach a header to, so the policy is built once, at prerender, by the same `contentSecurityPolicy()`. `modules/static-routes.ts` hashes the executable inline scripts of every generated page (`inlineScripts()`, so `application/ld+json` data blocks do not count, as in the dynamic plugin) and fails the build, naming the pages, if they differ; with `noScripts` it is the theme init script on all of them. The result is one `/*` rule in `_headers` (Cloudflare Pages, Netlify) with the policy and `SECURITY_HEADERS`, and the same policy in a `<meta http-equiv>` on each page for hosts without `_headers`, without `frame-ancestors` (a meta cannot carry it; `report-uri` and `sandbox` are not used). Image and media origins are empty: `_ipx/` and `_media/` are same-origin. Limits: a host that ignores `_headers` gets no `frame-ancestors`, no `X-Frame-Options` and no HSTS; an inline `onerror` is removed from the HTML (the hash CSP blocks inline handlers). `_headers` is checked against Cloudflare Pages' limits (100 rules, 2000 characters per line) and a page without `<head>` fails the build.

**Amendment (2026-10-07, #243, PR 6): search.** Pagefind runs WebAssembly, so static builds add `'wasm-unsafe-eval'` to `script-src` on every page (`_headers` has one rule, and the meta) through the `wasmEval` option of `contentSecurityPolicy()`, off by default: the dynamic policy is byte-identical. It allows compiling WebAssembly, not `eval()` or `new Function()`. The island that loads Pagefind is a `'self'` file (`/_islands/search-<hash>.js`, then `/pagefind/pagefind.js` and its worker), never an inline script, so the script hashes do not change. `/_islands/*` is immutable (hashed names); `/pagefind/*` is revalidated, because its entry files keep their names across builds.

**Amendment (2026-10-07, #243, PR 7): `formOrigins`.** `contentSecurityPolicy()` takes `formOrigins` (default none, so the dynamic policy is byte-identical) and adds those origins to `form-action` after `'self'`, in the static `_headers` and in the meta. Values go through `cspOrigin()`: `URL.canParse`, then protocol, host and port only; a host with anything outside letters, digits, hyphens and dots (`*`, `;`, `%`, spaces) is dropped and a trailing dot is removed, so a value cannot add a wildcard or a directive. `imageOrigins` goes through it too. The static newsletter uses the origin of `NUXT_PUBLIC_NEWSLETTER_FORM_ACTION` (`formActionOrigin()` in `app/helpers/newsletterForm.ts`; the action must be `https:`, or `http:` on localhost for tests). Chrome checks `form-action` on the redirects after the post too, so the provider's redirect must stay on that origin or land on this site (`'self'`); Buttondown's error pages are on `buttondown.com`, but where a success redirect lands (a custom newsletter domain, for one) is unverified and must be checked with a real subscription on a preview deploy. This PR adds no variable for redirect origins: a provider that redirects elsewhere needs one (not done until a real case exists).

**Amendment (2026-10-07, #247, implemented in PR 5): worker containment.** A runner that executes the reader's code (SQL, Python, JavaScript) lives in a dedicated Worker script under `/_islands/workers/`, and the response that serves it carries its own policy, `workerPolicy()`: `default-src 'none'`, `connect-src` limited to `<site origin>/_islands/runtimes/` (where the self-hosted runtimes are fetched from; a bare path is not a valid CSP source, so the origin comes from `NUXT_PUBLIC_SITE_URL` at response or build time, and the policy falls back to `'self'` when it is unset; *superseded: there is no fallback, see the 2026-10-08 amendment*), and `script-src 'self' 'wasm-unsafe-eval'`. A worker script's CSP comes from its own response, not from the page, so the page's policy stays as it is. In `dynamic` the header is set by a `routeRules` entry for `/_islands/workers/**` (*superseded by the 2026-10-08 amendment below: a Nitro plugin on the `request` hook sets it*); in `static` by a rule in the generated `_headers` file (`headersFile`), which has the same shape as the `/*` rule and counts against the same Cloudflare Pages limits. The worker deletes the network globals (`fetch`, `XMLHttpRequest`, `WebSocket`, `importScripts` after loading) once its runtime is loaded, so the policy is the second layer, not the first. Pages that contain a playground get `worker-src 'self'` and `'wasm-unsafe-eval'` from the registry's `workerSrc` and `wasm` (ADR 0006 amendment); pages without one keep today's policy.

**Why not a sandboxed iframe.** `<iframe sandbox="allow-scripts">` gets an opaque origin, and a Worker cannot be started from an opaque origin against a same-origin script, so the code would run on the iframe's main thread; an infinite loop then freezes the iframe's event loop and, in browsers that share a process, the page (a Worker can be `terminate()`d, an iframe cannot be interrupted). It would also need `frame-src`/`child-src` and a `postMessage` bridge with origin checks, and another document per playground. The Worker plus `workerPolicy()` gives the same isolation from the DOM and cookies (a Worker has neither) with a hard stop.

**Amendment (2026-10-08, #247, PR 5): where the Worker header is set, and no `'self'` fallback.** The design said a `routeRules` entry for `/_islands/workers/**`. That does not work here: `routeRules` headers are fixed at build time, but `NUXT_PUBLIC_SITE_URL`, which names the origin in `connect-src`, is runtime config (set by hand in production), and Nitro serves public assets before any server middleware, so a middleware never sees the request. The header is set by a Nitro plugin on the `request` hook (`server/plugins/workerPolicy.ts`), which runs first and reads the runtime config; the static build still writes its rule in `_headers`. The plugin does nothing in `nuxt dev`, like the page CSP. Static builds send `worker-src 'self'` on every page (one policy in `_headers`): it only restates what `script-src` already allowed for Workers, and Pagefind's Worker is a same-origin file too. e2e proves in Chromium, Firefox and WebKit that the policy sent with the Worker script is the one enforced (the Worker can fetch `/_islands/runtimes/` and compile WebAssembly, and cannot fetch another path or origin, nor call `eval()`). A `connect-src 'self'` fallback for an unset `NUXT_PUBLIC_SITE_URL` would let the Worker fetch anything of the site, so it is gone: without a valid origin the dynamic server logs an error at boot and answers 503 for the Worker scripts, and a static build fails. The path is decoded and normalised before it is compared (`/_islands/%77orkers/` gets the policy). Only the Worker compiles WebAssembly, so the page gets `worker-src 'self'` but not `'wasm-unsafe-eval'`. The Worker also removes the storage and network members it can reach, but dynamic `import()` cannot be removed (it reads scripts `script-src 'self'` allows), and every new runtime needs that audit again because it may hold its own reference to `fetch`.

**Amendment (2026-10-08, #247, PR 7): the JavaScript runtime.** Reader JavaScript runs in QuickJS compiled to WebAssembly inside the Worker, so the Worker policy is unchanged: `'wasm-unsafe-eval'` compiles QuickJS (Chromium, Firefox and WebKit, e2e), and `'unsafe-eval'` is not needed. Audit of the runtime: its `.wasm` is fetched while the runtime loads, before the network globals are removed; the guest gets only `console`, so it has no `fetch`, timers, `WebAssembly`, `self` or `import()` target; `eval` and the `Function` constructors throw in the guest. The interpreter's interrupt handler (4 s, or the output cap) stops a loop inside QuickJS and `terminate()` at 5 s is the backstop; QuickJS has a 32 MB memory limit and a 128 KB stack, and the WebAssembly memory has a 128 MB ceiling because QuickJS's own limit does not count every allocation. `docs/security.md` has the details.

**Amendment (2026-10-08, #247, PR 6): Python (Pyodide) under the same Worker policy.** Pyodide was the runtime most likely to need `'unsafe-eval'`. It does not: the Worker policy is unchanged (`default-src 'none'; script-src 'self' 'wasm-unsafe-eval'; connect-src <origin>/_islands/runtimes/`) and Pyodide 314.0.7 starts and runs Python on Chromium, Firefox and WebKit. It compiles its WebAssembly module (`'wasm-unsafe-eval'`) and `import()`s `pyodide.asm.mjs` from `/_islands/runtimes/` (`script-src 'self'`); the `eval()` and `new Function()` that Python code can reach (`js.eval`, `js.Function`, `pyodide.code.run_js`) become an `EvalError`, as intended. The re-audit the earlier amendments asked for found that Pyodide keeps no reference to `fetch` or `XMLHttpRequest` of its own (its loaders call the global at the time, and `pyfetch` reads `js.fetch`), so removing the globals after the load also cuts `pyfetch`, `open_url` and `loadPackage`. The `js` module is also restricted: `loadPyodide` gets a small frozen `jsglobals` (timers, `console` and the language's constructors; no `postMessage`, `self`, `globalThis`, `WebAssembly`, `ArrayBuffer`, `crypto`, `Blob` or `URL`). That is an extra layer, not the boundary, which stays the Worker policy plus the removal of the globals; `pyodide_js` still reaches Pyodide's internals. Reader code reaches an in-memory file system and Pyodide's own API, and no network, storage, eval or `postMessage`; the interpreter is shared by the Python blocks of a page (a fresh namespace per run, not a fresh interpreter), and its heap has the engine's 4 GB ceiling, which cannot be lowered. The remaining surface and the tests that pin it are in `docs/security.md`. The Worker also starts the 5 s clock once per run (a second `started` is ignored). Review found one route to the real scope through the timers (a callback runs with `this` set to the Worker's scope, which `create_proxy(f, capture_this=True)` receives); the timers of `jsglobals` are wrappers that call the callback with the reader's arguments only. Background work (asyncio tasks, timers) is cancelled when a run ends, and the Worker is replaced if a task will not stop. The Python files live in a folder of their own, `runtimes/pyodide-<hash>/`, because Pyodide finds its files by name next to each other; the hash covers their content, as `/_islands/` is immutable. One rule came out of the browsers: a runtime chunk must not import a module the Worker script holds (WebKit evaluates the Worker script twice then); the islands build fails if it does.

**Amendment (2026-10-08, #246, PR 8): the model of a `scene`.** The scene island fetches a `.glb` with `fetch()`, so a page that renders `<micelio-scene data-model="…">` needs the model's origin in `connect-src`. Dynamic pages: `sceneModelOrigins()` reads the `data-model` of each `<micelio-scene>` in the rendered HTML and adds its origin (through `cspOrigin()`) after `'self'`, but only when that origin is one the site already trusts for media (`NUXT_PUBLIC_STRAPI_URL`, `NUXT_MEDIA_URL`); a site path, another origin or a host that would change the policy adds nothing. Every other page keeps `connect-src 'self'` byte for byte. Static builds copy the `.glb` into `/_media/` like images (`data-model` is rewritten with the `src` and `poster` of media tags, only on `<micelio-scene>`), so the URL the island reads is `'self'` and the one policy of `_headers` gets no new source. The copy accepts a `.glb` by its bytes (glTF magic, version 2, header length equal to the file size, at most 20 MB) because hosts send any content type for it; a `.gltf` is refused (it names external buffers). The model's host must allow the site with CORS (`Access-Control-Allow-Origin`) in dynamic mode, since `fetch()` is not a plain image load.

**Amendment (2026-10-08, #245, PR 1): hashed `speculationrules`.** Static and landing builds add one `<script type="speculationrules">` to every generated page (`injectSpeculationRules()`, in the `prerender:generate` hook, so the error shell `404.html` has it too). The browser checks that script against `script-src`, so `speculationrules` joins `EXECUTABLE_TYPES` in `inlineScripts()` and its SHA-256 goes into the static `_headers` and the per-page meta like the other inline scripts; the dynamic header never sees one. The rules are the same on every page (`speculationRules()`, `app/helpers/speculation.ts`), so the hash is one and `scriptHashDisagreements` still passes. The `Speculation-Rules` response header was not used: it points to a rules file that is fetched from a URL, which needs its own `Content-Type` (`application/speculationrules+json`) and CORS-free same-origin serving on every host (Cloudflare Pages and Netlify `_headers` can set it, a plain file server cannot be assumed to), and a `<meta>` fallback cannot carry it. The inline script works on any host and needs no extra request.

**Amendment (2026-10-08, #246, PR 9): the scene island adds nothing to the policy.** The island's script and chunks are `'self'`; Three.js needs no `eval`, no `wasm-unsafe-eval` and no worker. The canvas is not an image or a connection. The model is fetched from `connect-src` (PR 8's origin, or `'self'` in static builds), and a `.glb` that embeds images shows them through `data:` URLs (`img-src` has `data:` in every mode; `blob:` is only in the dynamic policy). The registry entry therefore has no `csp`. A shadow root's `<style>` is covered by `style-src 'unsafe-inline'`.
