# Security model

What the frontend trusts, which credentials it uses to reach Strapi, and how each endpoint is protected. The input, output and status codes of each endpoint are in [openapi.json](openapi.json), and its caching and behaviour in [api.md](api.md). Keep it in sync when a route or a Strapi call changes. How it measures up against OWASP ASVS 5.0.0, requirement by requirement, is in [security/asvs.md](security/asvs.md).

## Credentials towards Strapi

The data the frontend handles and the protection of each level are in [Data classification and protection](security/data.md). The browser never talks to Strapi: every call goes through the Nitro server, built with `strapiUrl()` and, when it needs the API token, `strapiFetch()` (`server/utils/strapi.ts`).

| Credential | Where it comes from | Used for |
| --- | --- | --- |
| API token | `NUXT_STRAPI_API_TOKEN`, a **Custom** token created for this frontend | Content, comments, search, feeds and newsletter subscribers |
| None (public role) | — | Fediverse stats and ranking |
| User JWT | `__Host-micelio_session` cookie (`httpOnly`, `secure`, `sameSite=lax`, `Path=/`, no `Domain`, 7 days), set at sign-in | `/api/users/me` (profile and account deletion) |
| Editor JWT | Same cookie, for a user with the Editor role | Draft list and draft preview |
| None | — | Sign-in, registration, password reset and email confirmation (`/api/auth/*` in Strapi) |

### Permissions of the API token

Create a **Custom** token, never Full Access or Read Only, with exactly these permissions:

| Content type / plugin | Actions | Why |
| --- | --- | --- |
| Article | `find` | Blog list, article page (looked up by slug), reading path, RSS feeds. The search route (`/api/articles/search`) is public in the backend and needs no permission |
| Category, Tag | `find` | Filters and counts |
| Author | `find` | Author of an article (`populate` of the article routes) |
| About | `find` | About page |
| Page | `find` | Section pages (`/api/pages/:slug`, looked up by slug through the filtered `find`; `findOne` is not granted and not needed) |
| Site-setting | `find` | Site identity and modules (`/api/site`, RSS feeds, newsletter emails). Without it Strapi answers 403 and everything falls back to `app.config.ts` |
| Comments (plugin) | read (hierarchy and flat), create | Comment threads and guest comments |
| Subscriber | `lookup`, `create`, `update`, `delete`; `find` stays for the previous release line | Newsletter: subscribe, confirm, unsubscribe. `lookup` is `POST /api/subscribers/lookup` with `{ field, value }` in the body, so no email or token is in a URL (V14.2.1). Tokens are stored as SHA-256 hashes and looked up by hash (`hashToken`, `server/utils/subscribers.ts`) |

`update` on Subscriber is easy to miss: without it a subscription is created but confirming it fails with a 500. Without `lookup` every subscribe, confirm and unsubscribe fails: the frontend of this line needs a CMS that serves the route (`micelio-cms` from the release that added it). The frontend no longer calls `GET /api/subscribers`.

In production the server refuses to boot when `NUXT_PUBLIC_STRAPI_URL` or `NUXT_UMAMI_URL` is plain `http://` to a host outside a private network (`insecureUpstream`, `server/lib/upstreams.ts`; [ADR 0011](adr/0011-refuse-plain-http-upstreams.md)): the token, the visitors' sessions and the analytics payload would cross the internet in the clear. `https`, loopback and private addresses, `localhost`, dotless service names, `.internal` and `.local` pass; TLS inside a private network is the operator's call.

Who may hold each secret, how long it lives and the algorithms in use are in [Keys, secrets and algorithms](security/keys.md).

The token is a server-side secret. It must only be set as `NUXT_STRAPI_API_TOKEN`: plain `STRAPI_API_TOKEN` is ignored at runtime, and the server refuses to start with `Missing runtime settings` when it is empty. Rotate it in Strapi (Settings → API Tokens) if it is ever printed or shared, and delete tokens nobody uses. A static build (`npm run generate`, ADR 0006) reads content at build time, only from `NUXT_STRAPI_API_TOKEN` in the build environment, and **must be given the CMS `build` token** (`BUILD_API_TOKEN` in micelio-cms, created by `src/migrations/api-tokens.ts`), never the frontend token, which can read and delete subscribers. The `build` token is Custom and find-only: Article, Category, Tag, About, Site-setting, Page and Author `find`, and nothing else (no comments, no subscribers, no writes). The route list (`modules/static-routes.ts`) and the prerendered pages call the same read routes as the dynamic site (articles, pages, site settings, categories, tags, authors, about). The generated site holds no token and calls no API.

### Lifetime and rotation of the CMS credentials

The frontend authenticates to the CMS with two static secrets: the API token (`NUXT_STRAPI_API_TOKEN`) and, when set, the forwarder secret (`NUXT_STRAPI_FORWARDER_SECRET`). ASVS V13.2.1 prefers credentials that do not live forever; this is the policy and why it is not shorter.

| Credential | Lifetime | Rotate |
| --- | --- | --- |
| Frontend API token | No expiry (`lifespan: null`, set by `micelio-cms` `src/migrations/api-tokens.ts`) | At least every 90 days, at once when it was printed or shared, and when someone who held it leaves |
| Build token (`BUILD_API_TOKEN`) | No expiry, find-only | Same schedule |
| Forwarder secret | No expiry | Same schedule |

An expiry would not make the site safer by itself: nothing renews a token that lapses, so the site would start answering 401 on the day it does. Rotation is therefore a scheduled operator task; the decision and the conditions under which it is revisited are [ADR 0012](adr/0012-static-cms-credentials.md).

To rotate the API token, generate a new random value of at least 32 characters. Where the CMS creates the token from `FRONTEND_API_TOKEN` (or `BUILD_API_TOKEN`), set the new value there and in `NUXT_STRAPI_API_TOKEN`; the CMS replaces the key when it boots (`ensureEnvToken`). Restart the CMS first, then the frontend: until the frontend restarts, its calls to the CMS answer 401. Where the token was created by hand, create a new one in Strapi with the same permissions, set it in the frontend, and delete the old one. Rotate the forwarder secret on both sides together (`RATE_LIMIT_FORWARDER_SECRET` in the CMS); while the two differ, the CMS ignores the visitor's address the frontend sends and limits per server, and logs `a request sent a wrong forwarder secret`.

### What the public role must allow

The only anonymous calls are the fediverse stats and ranking routes, public by design in the backend (the sitemap now uses the API token like the feeds, so the public role needs no `find` on Article). Subscribers and users must stay closed to the public role (403); check it with:

```bash
curl -s -o /dev/null -w '%{http_code}\n' https://api.bogdev.com.co/api/subscribers   # 403
curl -s -o /dev/null -w '%{http_code}\n' https://api.bogdev.com.co/api/users         # 403
```

## Frontend endpoints

Every request body and query is validated with a zod schema (`server/schemas/`) or an equivalent check before any call to Strapi; unknown fields are dropped.

The routes of a module switched off in `site-setting.modules`, or off for lack of configuration, answer 404 before any of these checks (`server/middleware/modules.ts`, docs/api.md "Modules"). Turning a module off is therefore also a way to close its endpoints.

| Endpoint | Access | Protections |
| --- | --- | --- |
| `GET /api/posts`, `/api/posts/:slug`, `/api/search`, `/api/categories`, `/api/tags`, `/api/about`, `/api/reading-path`, `/api/site` | Public | Query schema: known locales only, `pageSize` ≤ 50, slugs, search ≤ 200 chars; a category is checked for the shape of a slug and then against the CMS list (`loadCategories`), never against a constant. An unknown slug-shaped category or tag in `/blog/category/<slug>` or `/blog/tag/<slug>` costs one server render and one filtered `/api/posts` call (a cache miss per slug, since the page starts the posts request while it waits for the category list) before the page answers 404; it falls under the same rate limits and ISR caching as any page |
| `GET /api/pages/:slug` | Public | Slug checked against the Strapi uid shape and locale against the known ones before any Strapi call; the response is rebuilt from a zod schema (unknown sections and fields dropped). Links: `http(s)`, `mailto:` or a path with one leading `/` and no backslash (`//host` and `/\host` are open redirects in browsers). Media URLs: site paths or the image origins of the CSP only. `canonicalURL` only on the site origin, `metaRobots` only known directives. Markdown comes out as sanitized HTML (`sanitize-html`, same options as articles). Only published content is read (`find` without `status=draft`). Post lists: at most four resolved per page. No rate limit, as on `/api/posts/:slug`: a random slug costs one Strapi call, and the 5 min cache (`loadPage`) bounds repeated hits on the same key; not found and errors are not stored |
| `GET /api/comments`, `/api/comments/flat` | Public | Relation must be `api::article.article:<documentId>`; pagination and sort validated; email and hidden comments never returned |
| `POST /api/comments` | Public | Same-origin check, 10 per IP (an IPv6 address counts by its /64) every 10 min, allow-listed fields and lengths, author id set by the server |
| `GET /api/fediverse/stats`, `/api/fediverse/stats/:documentId` | Public | Document id pattern, at most 50 ids |
| `POST /api/newsletter/subscribe` | Public | Same-origin check, 10 per IP (an IPv6 address counts by its /64) and 3 per email every hour, and 100 confirmation emails an hour in total whoever asks; same answer for new and confirmed addresses |
| `POST /api/newsletter/confirm`, `POST /api/newsletter/unsubscribe` | Holder of the emailed token | Token format check; confirm checks the same origin and is sent by a button on `/confirm`, so a link scanner that only fetches the link confirms nothing; unsubscribe also accepts RFC 8058 one-click POSTs from mail providers, so it has no origin check |
| `POST /api/auth/login`, `register`, `forgot-password`, `reset-password`, `resend-confirmation`, `confirm-email`, `logout` | Public | Same-origin check, body schema, `no-store`; the CMS rate-limits the auth routes per visitor (see "Client IP and rate limits") |
| `POST /api/auth/change-password` | Session + current password | Same-origin check, body schema (new password at least 10 characters and different from the current one), `no-store`; the CMS re-checks the current password with the person's own JWT and answers a new JWT that replaces the cookie |
| `GET /api/auth/me` | Session | `no-store` |
| `DELETE /api/auth/me` | Session + password | Same-origin check, username and password re-checked by Strapi |
| `GET /api/drafts`, `/api/drafts/:documentId` | Editor | Answers 404, not 403, to anyone else; `no-store` |
| `/feed.xml`, `/feed/*.xml`, `/sitemap.xml`, `/robots.txt` | Public | Read only |
| `/.well-known/security.txt` | Public | Read only. The `Contact` is the CMS's `securityContact`, public by design and never a private address; the route validates it again (`mailto:` or `https://`, one line, printable ASCII) so a stored value cannot add a header, and answers 404 without a valid one. It reads the site settings with the API token already granted for `site-setting` (`find`): no new permission |

Rate limits of comments and the newsletter are in memory (`server/utils/rateLimit.ts`): they reset when the container restarts and are per instance. They track at most 10 000 keys: when the map is full the oldest windows are dropped, so a flood of new addresses costs a bounded amount of memory and one pass over the map per thousand keys, not per key. An IPv6 address is counted by its /64 (`ipBucket`), as the CMS does, because one network holds 2^64 addresses. The CMS has its own limits (micelio-cms `docs/RATE_LIMITING.md`); a CMS 429 on comments, the newsletter or the auth routes reaches the browser as a 429 with its `Retry-After` and the same message as the route's own limit.

### Client IP and rate limits

The visitor's address (`clientIp()`, also used for the Umami proxy) is not taken from the leftmost `X-Forwarded-For` entry, which the visitor writes. `NUXT_TRUST_PROXY` says how far the header is trusted, the same model as the CMS's `TRUST_PROXY`; nothing depends on a particular proxy:

| `NUXT_TRUST_PROXY` | Meaning |
| --- | --- |
| `private` (default) | Read the header only while the socket peer and each hop, from right to left, are loopback, private, unique-local or link-local; the first public entry is the visitor. A public peer is never trusted |
| `N` | Exactly `N` trusted proxies: the visitor is the `N`-th entry from the right. A shorter chain falls back to the socket address |
| `10.0.0.0/8,203.0.113.7` | Trust only those proxies (addresses or CIDR ranges; `private` stands for the private ranges). An empty prefix or `/0` is refused |
| `false` | Never read the header: the socket address |

`true` is refused at startup because it trusts any header. `NUXT_PROXY_IP_HEADER` (default `X-Forwarded-For`) names another header, e.g. a CDN's, for the same chain. Ports, brackets, zones and `::ffff:` prefixes are normalised. Choose the value that matches the real proxy chain: with a public hop in front that is not listed, every visitor would share the proxy's address.

Nitro runs environment values through `destr`, so `false`, `0`, `2` and `true` arrive as boolean or number; `NUXT_TRUST_PROXY=true` is refused either way. If the container is published directly with no reverse proxy (Docker's userland proxy or the gateway shows up as a private address), the default `private` would trust a visitor's own `X-Forwarded-For`: set `NUXT_TRUST_PROXY=false`, or the exact CIDR of the proxies you run.

The same setting decides whether `X-Forwarded-Host` and `X-Forwarded-Proto` are read when the same-origin check of the auth, comment and subscribe routes (`assertSameOrigin`) works out the site origin: never with `false`, always with a hop count, and with `private` or a list of ranges only when the socket peer is a trusted proxy (`trustsForwardedHost()`). A visitor who reaches the server directly cannot make a foreign `Origin` match by sending those headers.

The server calls the CMS from one address, so the CMS limits would be shared by all visitors. With `NUXT_STRAPI_FORWARDER_SECRET` set (at least 32 characters, the same value as `RATE_LIMIT_FORWARDER_SECRET` in the CMS; shorter stops the boot; it is read from the raw environment and used untrimmed, as the CMS compares it), every CMS call made on behalf of a visitor sends `X-Micelio-Forwarder-Secret` and `X-Micelio-Client-IP` (the address above, only when it is a valid IP). Without the secret on both sides the CMS limits are per server, not per visitor. The boot also stops if the secret is set and `NUXT_PUBLIC_STRAPI_URL` is neither `https` nor a private address (loopback, private range, `localhost`, a dotless service name, `.internal`, `.local`), and no CMS call follows a redirect (`redirect: 'error'` in `strapiRequest`), so neither the token nor the forwarder secret leaves the configured origin.

What forwards:

- Every browser request to `/api/*` (comments, newsletter, auth, posts, search, tags, about, reading path, drafts, fediverse; `/api/categories` and the category checks read the shared cached `loadCategories`, which does not forward), with the address resolved from its socket.
- Server-side rendering. SSR calls `/api/*` in process, with no socket address, through Nuxt's `event.$fetch` (`useRequestFetch`, `useFetch`, and `useStrapi`). `server/plugins/internalClientIp.ts` adds the outer request's resolved address and a per-process random nonce (`x-micelio-internal-ip`, `x-micelio-internal-nonce`) to those calls; `clientIp()` accepts them only when the socket has no remote address and the nonce matches (timing-safe). A request from outside carrying those headers, with a wrong nonce or none, is ignored (and has a socket address anyway). The nonce never leaves the process; the headers are never sent to the CMS or to Umami. A plain global `$fetch` carries nothing, so SSR code that calls `/api` must use `useRequestFetch()`.

Notes on what counts as a visitor:

- An uncached server-side render counts against the visitor who triggered it, so crawlers and visitors behind one NAT share a bucket. ISR/page caching keeps this cheap: a cache hit makes no CMS call, and a cached render is never attributed to a visitor on purpose (Nitro's cache handler builds its own event, which does not carry the internal headers).
- `useFetch(..., { server: false })` runs in the browser, so its request reaches `/api/*` directly and is forwarded like any browser request.
- The internal headers are added only to same-origin relative paths (`/api/...`); an absolute URL or `//host` never gets them. `clientIp()` removes them from the request after reading, so `getProxyRequestHeaders` cannot carry them onward.
- `NITRO_UNIX_SOCKET` (listening on a unix socket) is unsupported for per-visitor limits: there is no remote address, so every visitor resolves to `unknown` and nothing is forwarded.
- A secret set only in `nuxt.config.ts` goes through `String()` and cannot be recovered if it looks like a number; set it by environment variable.

What does not forward (the CMS counts these against the API token's bucket): the cached site settings and pages (`loadSite`, `loadPage`, `loadCategories`, shared between visitors), the feeds and the sitemap (crawler and CDN-cached traffic), and the static build. A call without the visitor, such as a failed address (`unknown`), sends no headers.

`strapiFetch(path, { event })` adds the headers, and every call to the CMS goes through it (`test/strapiRequest.test.ts` fails on a `$fetch(strapiUrl(...))` or a `strapiFetch` outside the exceptions above whose options lack `event`), including the token-less ones (`auth: 'none'`) and those with a user's JWT (`auth: { jwt }`). Extra headers can never carry `Authorization`. The auth calls wait up to 30 s (register and password mails are sent inside Strapi); other calls 10 s.

A CMS 429 reaches the browser as a 429 with the CMS's `Retry-After` (a positive number, at most 3600) and, where the route would otherwise degrade (search, fediverse ranking and stats), `Cache-Control: no-store`. The Umami proxy replaces `X-Forwarded-For` and `X-Real-IP` with the resolved address and drops the other client address headers (`CF-Connecting-IP`, `True-Client-IP`, `X-Client-IP`, `Forwarded`…); set Umami's `CLIENT_IP_HEADER` to `x-forwarded-for` or `x-real-ip`. A redirect from Umami is not passed on: the proxy answers 502. The static build does not follow a redirect when it copies media either: a media host that redirects fails `generate` with the URL named, and the media origin must point at the final URL. The proxy also drops `Referer`, the cookie and the authorization header: the address of the page can carry a one-use secret in its query (a password-reset code, a newsletter token), so neither the tracker (it is told to leave the query string out, `data-exclude-search`) nor the proxy sends it to Umami, and the pages that open from such a link send no `Referer` at all (`Referrer-Policy: no-referrer`) and take the secret out of the address bar once they have read it (`useForgetQueryParam`). The secret is a credential: keep it out of logs and of the repository, and rotate both sides together.

The article, post list, draft preview and about routes, and the post cards of a page, answer from an allow-list of fields (`server/lib/publicShapes.ts`, ASVS V15.3.1), not from what Strapi returns: a field the pages do not read, or one a later CMS version adds, is not sent to the browser. The Strapi token needs no new permission; the article and About queries name the nested components and the fields of images, categories and authors instead of `populate: '*'`. Each comment is rebuilt by `toPublicComment` from a list of public fields (`PUBLIC_FIELDS`); the envelope of the flat comments list (`publicCommentsPage`) and each row of the draft list (`publicDraftRow`) are rebuilt from an allow-list too.

## Authentication and sessions

People sign in with a password: one factor, an account per email address. Accounts are readers (they comment and subscribe) or editors (they also preview drafts); an administrator gives the Editor role by hand in the CMS admin panel. This section says which ways in exist, what each one enforces, and how long a session lasts (ASVS V6.1.3, V6.3.4, V7.1.1, V7.1.2). Why there is no second factor is in [ADR 0003](adr/0003-session-in-httponly-cookie.md), amendment of 2026-10-14.

### Authentication pathways

| Pathway | Entry point | What it enforces |
| --- | --- | --- |
| Sign in | `POST /api/auth/login` of the frontend, which calls `POST /api/auth/local` of the CMS | Same-origin check, body schema, `no-store`; CMS limits per client (10 per 60 s per route), per login identifier across all addresses (10 per 15 min) and a confirmed email before the first sign-in |
| Sign up | `POST /api/auth/register`, then the CMS register route | The same checks, a password of at least 10 characters in the frontend, and 5 emails per address per hour in the CMS; the account cannot sign in until its email is confirmed |
| Email confirmation | The link in the email lands on `/account/confirmed?confirmation=<token>`, which shows a button; the click calls `POST /api/auth/confirm-email` of the frontend, then `POST /api/auth/email-confirmation` of the CMS (ASVS V3.5.3: a sensitive function is not a GET). The CMS `GET` of the same path still confirms and redirects to `/account/confirmed` until it only redirects with the token | Same-origin check, a body schema (40 lowercase hexadecimal characters), `no-store`; one-use token and 10 requests per 60 s per client in the CMS; no session is set; a scanner that opens the link confirms nothing; the token leaves the address bar and is never logged |
| Resend confirmation, forgot password, reset password | `POST /api/auth/resend-confirmation`, `forgot-password`, `reset-password` of the frontend, then the CMS routes | Same-origin check, body schema; 5 emails per address per hour; the same answer whether or not the address has an account |
| Change the password | `POST /api/auth/change-password` of the frontend, which calls the CMS route with the person's own JWT | Session, same-origin check, the current password asked again, and a new password of at least 10 characters that differs from it; the cookie is renewed with the JWT the CMS answers |
| Delete the account | `DELETE /api/auth/me` | Session, same-origin check, and the password asked again |
| Third-party sign-in | `/api/connect/*` of the CMS | Off unless the operator enables a provider in the CMS admin panel; the frontend has no flow for it. A site that turns one on adds a pathway with its own strength and must document it here |
| CMS admin panel | `/admin` of the CMS | Separate administrator accounts, with their own limits (20 per 300 s per client); not part of the frontend |

The CMS routes `/api/auth/*` and `/api/users/me` can also be called directly by anyone who reaches the CMS address. They carry the CMS limits listed above and the same confirmed-email rule. The 10-character minimum is enforced only by the frontend; a direct sign-up, reset or `change-password` call on the CMS is held to 8 characters, the lists of common and breached passwords and the context words (micelio-cms#177, `docs/security/authentication.md` there). The strength every pathway must hold is: a confirmed email, a password of at least 8 characters outside those lists, and the rate limits above.

### Sessions

| What | Value |
| --- | --- |
| Absolute lifetime | 7 days: the cookie `Max-Age` and the CMS JWT `expiresIn` are both 604800 seconds. A session is not extended while it is used |
| Inactivity timeout | None |
| Concurrent sessions | Not limited: every sign-in issues its own JWT and none ends another, so there is no maximum to reach and no behaviour for reaching it |
| Sign out | Clears the cookie of that browser. The JWT itself stays valid until it expires, which ADR 0003 accepts |

Why there is no inactivity timeout, which departs from some readings of NIST SP 800-63B: a password alone is authenticator assurance level 1, for which the guideline asks to re-authenticate at least every 30 days and asks for no inactivity limit; 7 days is stricter on lifetime. The accounts hold an email address and a username, comment, and (editors) read drafts, with no payment or other personal data. An inactivity timeout needs a server-side record of the last use, which a stateless JWT does not have; the CMS offers one only in its `refresh` session mode, which would supersede part of ADR 0003. It is left out by decision of 2026-10-14 and recorded as an accepted risk (ASVS V7.3.1 and V7.5.2); the ADR 0003 amendment has the reasoning. Check this against the current revision of the guideline when it changes, and when accounts hold more than they do.

### Request size

A request body is read within 64 KB (`readLimitedBody` in `server/utils/validation.ts`): a declared `content-length` over it, or bytes that pass it while they arrive (a chunked body has no length), are a 413 before the route runs, and the Umami proxy applies the same cap to its payload. The auth schemas bound what they accept (an email or identifier at most 254 characters, a password typed into a form at most 1024, a new password at most 72 bytes, a reset code at most 256 characters of letters, digits, `_` and `-`). A reverse proxy in front can set a lower cap; none is needed for the process not to hold a large body.

## Browser-side protections

- **HTTP methods**: `server/middleware/methods.ts` answers any method outside GET, HEAD, POST, PUT, PATCH, DELETE and OPTIONS (`TRACE` above all) with 405 and an `Allow` list, before any route runs.
- **Security headers** on every response (`SECURITY_HEADERS` in `app/helpers/securityHeaders.ts`): HSTS, `nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy`, COOP.
- **Content Security Policy** on every page, built in `server/plugins/contentSecurityPolicy.ts` from the rendered HTML: each inline script is allowed by its SHA-256, so `script-src` has no `'unsafe-inline'`; `object-src` and `base-uri` are `'none'` (the site sends no `<base>`). Every other response (API, feeds, files) carries `frame-ancestors 'none'`, set on `request`, and the Worker scripts and the theme assets carry it in their own policies. Images: the site, Strapi and `NUXT_MEDIA_URL`; frames: YouTube and Vimeo only. To allow a new image or embed domain, add it to `contentSecurityPolicy()` and to the `sanitize-html` options in `app/helpers/markdown.ts` together.
- **Speculation Rules** (static and landing, #245, ADR 0004 amendment): one inline `<script type="speculationrules">`, identical on every page, hashed into `script-src` like the other inline scripts (the browser applies `script-src` to it); the `Speculation-Rules` header is not used. The rules exclude `/api/*`, `/account*`, `/drafts*`, `/newsletter/*`, `/confirm*`, `/_theme`, `/pagefind/*`, `/_islands/*`, `/_media/*`, `*.xml`, `robots.txt` and links marked `[download]`, `[rel~=nofollow]` or `[data-no-speculate]`, so a prerender never loads a page with a side effect. They are built from constants, with no user input. Analytics must be added through the build (`NUXT_PUBLIC_UMAMI_WEBSITE_ID`) and the site rebuilt: if a host injects Umami by itself, the pages are still prerendered and may count pageviews nobody saw.
- **Static builds** (`static` and `landing`, ADR 0004 amendment): there is no server to send headers, so the build writes `.output/public/_headers` with one `/*` rule: the CSP (the hashes of the inline scripts of all pages, which must be identical or the build fails; no Strapi image origin, since `_ipx/` and `_media/` are same-origin) and the same `SECURITY_HEADERS`. Cloudflare Pages and Netlify apply it. Every page also carries the CSP in `<meta http-equiv="Content-Security-Policy">` for hosts without `_headers`; it lacks `frame-ancestors` and cannot send HSTS, `X-Frame-Options`, `Permissions-Policy` or COOP, so those hosts are weaker (GitHub Pages is not a reference host). `/_nuxt/*` (Vite hashes) and `/_media/*` (named after the SHA-256 of the bytes) get `Cache-Control: public, max-age=31536000, immutable`. `/_islands/*` (hashed names) is immutable too. The policy has `'wasm-unsafe-eval'` in `script-src` for Pagefind's WebAssembly (the search island, ADR 0004 amendment): it lets the browser compile WebAssembly, not run `eval()` or `new Function()`, and it applies to every page because `_headers` has one rule, and to every static build even when `search` is off in Strapi, because the build only fetches slugs and the module is read from Strapi when each page renders; the dynamic policy does not have it. `/pagefind/*` gets the revalidating rule below as well, since `pagefind.js` keeps its name across builds. `/_ipx/*` gets `public, max-age=0, must-revalidate`: its names carry the source URL, and Strapi keeps a file's URL when it is replaced, so an immutable rule would keep a replaced or taken-down image in browsers; revalidation (ETag) drops it on the next rebuild. Versioning the `_ipx` sources by Strapi's `updatedAt` would allow immutable later. Pages keep the host default. `/_media/*` also sends a second policy, `default-src 'none'; style-src 'unsafe-inline'; img-src 'self' data:; sandbox` (repeated policies only tighten), so an SVG opened directly runs nothing; the build copies only `image/*`, `video/*` and `audio/*` responses (and `.glb` models, checked by their bytes: see the scene bullet), only from Strapi's `/uploads/` and the media host, and only from real `<img>`, `<video>`, `<source>`, `<audio>` and `<micelio-scene>` tags (not code blocks). The build fails if a page has no `<head>` for the meta, or if `_headers` has a line over 2000 characters or more than 100 rules (Cloudflare Pages limits). With the newsletter on, `form-action` is `'self'` plus the origin of `NUXT_PUBLIC_NEWSLETTER_FORM_ACTION` (`formOrigins`, origin only and only plain hosts, never `*` or `;`; the action must be `https:`, so a typo cannot widen the policy to an arbitrary scheme); the visitor's email goes to that provider, which the privacy page names. Whether the host applies `_headers` to 404 responses must be checked on a preview deploy; the meta covers the CSP there. The output has no `200.html`, so hosts answer unknown paths with `404.html`.
- **Playground (runnable code, #247)**: the reader's code runs in a dedicated Worker, never on the page (no DOM, no cookies). The Worker script is a file of `/_islands/workers/` whose own response carries the policy of `workerPolicy()` (`app/helpers/securityHeaders.ts`): `default-src 'none'; script-src 'self' 'wasm-unsafe-eval'; connect-src <site origin>/_islands/runtimes/`. The origin comes from `NUXT_PUBLIC_SITE_URL` and must be the origin the site is served from; there is **no fallback**: with the URL unset or not a plain origin, the dynamic server logs an error at boot and answers 503 for `/_islands/workers/` (the run stays on its fallback), and a static build fails. No `eval()`, no other network. In `dynamic` the header is set by `server/plugins/workerPolicy.ts` on every request whose decoded, normalised path is in that folder (`%77orkers` and `./` count); in static builds by a `/_islands/workers/*` rule in `_headers`, repeated on top of the `/*` rule (repeated policies only tighten). A host without `_headers` support cannot set it for a static site; there only the next layer protects.
- **Playground, inside the Worker**: once the runtime is loaded the Worker deletes `fetch`, `XMLHttpRequest`, `WebSocket`, `WebSocketStream`, `WebTransport`, `EventSource`, `importScripts`, nested workers, `caches`, `indexedDB` and the storage, `locks`, service worker and beacon members of `navigator` (`app/helpers/workerSandbox.ts`). What cannot be removed is the dynamic `import()`: it only reads scripts the Worker policy allows (`script-src 'self'`), a same-origin GET at most. **Each new runtime needs this audit again** (the JavaScript and Python audits are in the bullets that follow): it may keep its own reference to `fetch` from before the removal, or open a path the list does not cover. SQL has no way to run JavaScript. A run lasts at most 5 s of its own code (then `worker.terminate()`), can be stopped, and what it leaves running is stopped when it ends (the Python runtime cancels its asyncio tasks and clears its timers), and its output is cut at 64 KB and written with `textContent`. The SQL engine limits what a query may allocate (`sqlite3_limit`: 1 MB per value, 100 KB of SQL, no attached databases, and a 64 MB heap when the build exports it), so a `zeroblob(1e9)` is an error, not a crash. Browsers without WebAssembly or Workers keep the code and its expected output. Chromium, Firefox and WebKit are tested for enforcing the Worker's own policy (`e2e/playground`, `e2e/static/playground.spec.ts`).
- **Playground, JavaScript runtime (#247)**: the reader's JavaScript runs in **QuickJS compiled to WebAssembly** (`quickjs-emscripten-core` + `@jitl/quickjs-wasmfile-release-sync`, 0.32.0, MIT; `app/islands/runtimes/javascript.ts`), inside the same Worker, never in the Worker's own realm: the Worker's `eval` is not used and a sandboxed iframe is not involved. It compiles under the Worker policy's `'wasm-unsafe-eval'` alone (no `'unsafe-eval'`; the e2e proves it on Chromium, Firefox and WebKit, with no CSP violation on the page or in the Worker). The guest sees only `console` (`log`, `info`, `warn`, `error`): no `fetch`, `XMLHttpRequest`, timers, `WebAssembly`, `self` or `postMessage` exist in it, `import()` has no module loader, and `eval` and every `Function` constructor throw (QuickJS needs its Eval intrinsic for the host to run the code, so a prelude closes them in the guest). Re-audit of `workerSandbox` and the policy for this runtime: the package's `fetch` of its `.wasm` happens during load, before the globals are removed, and the QuickJS module keeps no reference the guest can reach. Limits: the interpreter's interrupt handler stops the code after 4 s (an `Interrupted` error, also when the time ran out inside a promise job) or once it has written twice the output cap; it sees interpreted code only, so a long built-in call (`new Array(1e8).join('x')`) is left to `worker.terminate()` at 5 s, the backstop. QuickJS's memory limit is 32 MB, its stack 128 KB (higher values overflow the engine's native stack before QuickJS notices), and the WebAssembly memory has a hard ceiling of 128 MB because QuickJS does not count every allocation (a big array filled in a loop slipped past its limit); that memory is not given back, so a run that expired, ran out of memory or stack, filled the output or failed in the host makes the Worker answer with `recycle`, and the pool terminates and replaces that Worker (the next run reloads the runtime from the HTTP cache). A single `console.log` line and an error message are cut before they are kept or posted. Output is plain text, capped at 64 KB.
- **Python runtime** (Pyodide, #247 PR 6): CPython compiled to WebAssembly, the core interpreter and the standard library only, self-hosted under `/_islands/runtimes/pyodide-<hash>/` (`pyodide.mjs`, `pyodide.asm.mjs`, `pyodide.asm.wasm`, `python_stdlib.zip` and a lock file stripped of its ~300 packages; `modules/lib/pyodide-assets.ts`). No `micropip`, no package loading: `import micropip` is a `ModuleNotFoundError` and `pyodide_js.loadPackage()` knows no package. It runs under the **same Worker policy as SQL**, unchanged: the Worker needs `'wasm-unsafe-eval'` (to compile the module) and `script-src 'self'` (to `import()` `pyodide.asm.mjs`), and never `'unsafe-eval'`; Chromium, Firefox and WebKit run it (`e2e/playground/python.spec.ts`, `e2e/static/python.spec.ts`). Output is stdout and stderr in order, with the same 64 KB cap, 5 s timeout and Stop as SQL; each run gets a fresh namespace, and `input()` reads the end of the input.
  **What reader code can reach** (audited for Pyodide 314.0.7, each line is tested). *Not reachable*: the network (`from js import fetch`, `js.fetch(...)`, `XMLHttpRequest`, `WebSocket`, `EventSource`, `importScripts`, nested Workers and `BroadcastChannel` are gone from the Worker's scope, and Pyodide holds no reference of its own to them: `pyodide.http.pyfetch`, `open_url` and `pyodide_js.loadPackage()` fail with "fetch is not defined" and no request reaches the server), `eval` and `new Function` (`pyodide.code.run_js` cannot import `eval`, and `js.Object.constructor('...')` is an `EvalError`: the Worker policy has no `'unsafe-eval'`), `indexedDB` and OPFS (`navigator.storage` is gone, Pyodide's `IDBFS` finds no `indexedDB` to sync with), `caches`, service workers. `zoneinfo` finds no time zones: it needs the `tzdata` package, which is not shipped (no packages are).
  **The `js` module is restricted** (an extra layer, not the boundary). `loadPyodide` gets a small frozen `jsglobals` instead of the Worker's scope (`runtimes/python.ts`). Kept: the timers asyncio's loop needs (`setTimeout`, `clearTimeout`, `setInterval`, `clearInterval`, `queueMicrotask`, bound to the scope), `console`, and the language's own constructors (`Object`, `Array`, `Promise`, `Symbol`, `Error`, `TypeError`, `RangeError`, `JSON`, `Math`, `Date`, `Number`, `String`, `Boolean`, `BigInt`, `Map`, `Set`). Everything else is absent for Python, and tested to be: `postMessage`, `self`, `globalThis`, `WebAssembly`, `ArrayBuffer`, `crypto`, `Blob`, `URL`, `navigator`, `Request`, `Response`, `eval`, `Function`. What this layer is not: the boundary stays the Worker policy (`connect-src` limited to the runtimes folder, `script-src 'self'`, no `'unsafe-eval'`) plus the removal of the network and storage globals. A reference to the real scope can still come from Pyodide's own objects: `pyodide_js` (the API, `FS` and its file systems, `_module`, `_api`) reaches Pyodide's internals, and the language's constructors reach `Function`, which the policy blocks. One route was found and closed in review: a timer calls its callback with `this` set to the Worker's scope, and a Python proxy made with `create_proxy(f, capture_this=True)` would have received it. The `js` module's `setTimeout`, `setInterval` and `queueMicrotask` are wrappers that call the callback from an arrow of ours, with only the reader's own arguments, and refuse a string of code; `then`, `forEach` and the other callbacks of the kept constructors run with `this` undefined or the reader's own `thisArg`. All of it is tested on three browsers. No other route to `postMessage`, `self` or `globalThis` was found through `js`, `pyodide_js`, `pyodide_js._module` or `pyodide_js._api`, but the Pyodide API is large and its absence is not proved.
  *Reachable and accepted*: the interpreter's in-memory file system (`MEMFS`; `NODEFS`, `WORKERFS` and `NATIVEFS_ASYNC` have nothing to mount), `pyodide_js`, and the dynamic `import()` the earlier bullet describes (no way to call it with a reader's URL was found). No way to post to the page was found. If one existed, the page accepts only a reply with the id of the run in progress, shows its text, and starts the 5 s clock **once per run**: a second `started` is ignored (`lib/workerRunner.ts`), so a forged message cannot extend the limit. The ids are sequential and guessable, so a forgery is limited to the reader's own output.
  **Background work does not outlive a run.** An asyncio task or a timer the code leaves running would burn CPU with no clock and write into later runs, other blocks included. When a run ends (well or not) the runtime cancels every pending asyncio task and waits for it, then clears every live timer; a task that does not stop within half a second marks the interpreter as broken and the Worker is replaced (`recycle`). Tested: an interval and a task print, the run ends, and the next run's output has none of it. A fatal Pyodide error, a `MemoryError` or a `RecursionError` also replace the Worker.
  **One interpreter per page, a namespace per run** (decision of #247 PR 6). Each run gets a fresh namespace (`__name__ == '__main__'`, no variables of earlier runs), but the interpreter is shared by every Python block of the page: imported modules (and what the reader sets on them), `builtins`, `sys` and the in-memory file system persist between runs and between blocks, and an author's hidden setup code runs in the same interpreter. A block can therefore see or alter what another one left behind; the only one it can harm is the reader who ran both. A timeout, Stop or a crash terminates the Worker, and the next run starts a clean interpreter. `sys.stdout` and `sys.stderr` are put back before every run.
  **Memory**: not capped like SQLite's heap. Pyodide creates its own WebAssembly memory and has no maximum option, so the ceiling is the engine's 4 GB for a 32-bit module, and it cannot be lowered from outside. A program that allocates for ever grows the heap until the engine refuses (`MemoryError` or a crash of the Worker, which becomes an error) or until the 5 s timeout. The tests cover a loop of 50 MB chunks in all three browsers: it ends in an error and the page is alive. A device with little memory may still struggle before 4 GB. Output and error text are cut inside the Worker (128 K characters, counted in UTF-16 units) and again to 64 KB on the page, and `capOutput` slices a string before it encodes it, so a huge message is never encoded whole on the main thread.
  **Build trap, found in this runtime**: a runtime chunk (`runtimes/`) must not import a module the Worker script (`workers/`) also holds. WebKit then evaluates the Worker script a second time in the same Worker, so its `message` listener runs twice with state of its own (the runtime loaded again, with the network already removed: `Can't find variable: fetch`). `modules/islands.ts` fails the islands build when it happens (`runtimesImportingWorkers`). SQL had the same import since PR 5 (`MAX_OUTPUT_BYTES`), unnoticed because both listeners answered.
  **License**: `pyodide` is MPL-2.0, which `lint:licenses` allows; it is shipped unmodified. Its files are self-hosted: nothing is fetched from a CDN, and Pyodide's default of loading packages from jsDelivr is unreachable (no `fetch`, and the lock file has no packages).
- **Page CSP of a playground** (dynamic): a page that renders `<micelio-playground>` gets `worker-src 'self'` and nothing else (only the Worker compiles WebAssembly, under its own policy); every other page keeps its policy byte for byte. Static builds have one policy for all pages, so every static page gets `worker-src 'self'` (`'wasm-unsafe-eval'` was already there for Pagefind). Before, a static page had no `worker-src`, so Workers fell back to `script-src` (`'self'` plus hashes): the same set of Worker scripts is allowed, now stated explicitly. The SQL engine is `@sqlite.org/sqlite-wasm` (Apache-2.0), self-hosted under `/_islands/runtimes/`; nothing is fetched from a third party.
- **Scene models (#246)**: `section.scene` accepts a `.glb` only (the schema refuses `.gltf`, whose buffers are separate files), on a path under `/uploads/` or on a media origin of the CSP, as every media URL. The server renders it as `data-model` on `<micelio-scene>`. Dynamic: a page with a scene gets the model's origin in `connect-src` after `'self'` (`sceneModelOrigins()`, only an origin that is `NUXT_PUBLIC_STRAPI_URL` or `NUXT_MEDIA_URL`; nothing for a site path or any other host), every other page keeps `connect-src 'self'` byte for byte. The host must send CORS headers for the site (Strapi `strapi::cors` `origin`, the bucket's CORS rule), or the island stays on the poster. Static: the build copies the model into `/_media/` and rewrites `data-model` (only on `<micelio-scene>`, so a code block that shows the tag is untouched), so the island fetches from `'self'` and the single `_headers` policy gains no source. The copy accepts a response when its bytes are a glTF 2 binary (magic `glTF`, version 2, header length equal to the size, at most 20 MB) whatever content type the host sends, and fails the build otherwise; `/_media/*` keeps its sandbox policy. No Strapi token permission changes: `page.find` already populates `model`.
- **Scene island (#246)**: `<micelio-scene>` (`app/islands/scene.ts`) fetches the `data-model` URL with `credentials: 'omit'` and no referrer, only if it is http(s) and ends in `.glb` (`modelSource()`), cancels the body past 20 MB, and checks the glTF header before parsing (`isGlb()`). **Memory cap:** `glbProblem()` reads the JSON chunk of the bytes before `GLTFLoader` sees them, because Three.js allocates whatever the accessors say even when no data backs them (a few hundred bytes with one `VEC3` accessor of 2 billion floats asked for 24 GB). It sums `count × items × component bytes` over every accessor, sparse ones included, and refuses the model above 64 MB (`MODEL_MAX_ACCESSOR_BYTES`); it also refuses an embedded image over 8 MB or over 16.7 million pixels (PNG and JPEG headers are read; other formats only have the byte cap), a buffer or image whose `uri` is not a `data:` URL, and an invalid accessor. A refused model ends in `data-state="error"` and the poster stays; nothing is allocated. Cost of the check: one pass over the JSON. The origin gate is the page's `connect-src` (Strapi or media origin in dynamic builds, `'self'` in static ones). The parser is Three.js `GLTFLoader` with a loading manager that throws for any URL but `data:`, so a model cannot make the page request other files; images inside it become `data:` URLs read by `<img>`. Under reduced motion, Save-Data, without WebGL2, or after a lost context the page keeps its poster and downloads neither Three.js nor the model. `three` (MIT) is a production dependency pinned to an exact version, with `@types/three`. No `unsafe-eval`, no new directive.
- **Theme init script** (`modules/theme/init-script.mjs`): one inline script in `<head>` that sets `data-theme` and `data-scheme` before first paint. It is generated once per build from the active theme's modes (at most 6, so it stays under 2 KB), so its CSP hash is the same on every page and changes only between builds; no request data (locale, stored value, Strapi value) enters it. It only reads `localStorage` and never writes. Mode ids are limited to `[\w-]` because they go into the inline script, the CSS selectors and the `<html>` attributes. The server writes the first mode's `data-theme` and `data-scheme` into `<html>` in `server/plugins/themeMode.ts`, or Strapi's `defaultMode` plus `data-mode-default` when it equals a mode of the built theme (the value written is the manifest's id, never the Strapi string); the script ignores the server-written `data-theme`, so without `defaultMode` the system preference still wins on a first visit.
- **Rich text** from Strapi is rendered on the server with `marked` and always passed through `sanitize-html` before it leaves the API (`app/helpers/markdown.ts`, used by the post, about and draft routes). If rendering fails, the text is escaped, never passed through. The three `v-html` lint warnings point at that sanitized `html`.
- **Cookies**: only `__Host-micelio_session`, and only after signing in; the `__Host-` prefix means a sibling subdomain cannot set or overwrite it (ADR 0003, amendment of 2026-10-14). Until #422 a request with only an older name (`micelio_session`, or the pre-rename `bd_session`) is accepted and moved to the new name by `server/middleware/session-rename.ts` (same attributes, old cookie cleared, `/api/auth/**` and `/api/drafts/**` only, which are `private, no-store`). The old name is never written. The move restarts the 7 days once, so a moved session can last up to about 14 days in total. Logout and account deletion clear all three names.

## Themes

- **Build-time, operator-trusted.** `NUXT_PUBLIC_THEME` and `MICELIO_THEME_DIRS` are read by `modules/theme` at build. Whoever controls them controls the CSS and fonts that ship; they are not user input. Even so, the theme's `images/` is filtered when it is copied (below).
- **Strapi theme overrides.** `site-setting.theme` in Strapi (`accentOverrides`, `displayFont`, `defaultMode`, `themeId`) is input from CMS editors, resolved by `server/utils/theme.ts` with the site settings (`loadSiteCached`). A `themeId` other than the built theme is ignored and logged, and the list of overrides is capped. Validation and re-serialization prevent injection: each color is parsed to RGB and re-serialized to `#rrggbb` by `toHex()` (never interpolated); mode ids are matched by equality against the built theme's manifest; `displayFont` is validated against the enum (`displayFontId()`) when the theme is resolved, so `Site.theme.displayFont` is only ever a known value; invalid items are dropped individually, and the first override per mode is kept. The server generates one `<style id="theme-overrides">` block in SSR head, with the accent rules matching the whitelist regex `/^(?:\[data-theme="[a-z][a-z0-9-]*"\]\{--accent:#[\da-f]{6};--accent-soft:#[\da-f]{6};--accent-hover:#[\da-f]{6};--on-accent:#[\da-f]{6}\})+$/` (mode ids must be `[a-z][a-z0-9-]*` per ADR 0005 §2; this regex limits each value to 6 hex digits; any deviation logs an error and omits the block). The display font adds, to the same block, an `@font-face`, its fallback faces and `:root{--font-display:…}`, built only from a table keyed by the `displayFont` enum (family, weight range, latin `unicode-range`), the file's content hash (8 hex digits, `?v=`), the generated `app/assets/fonts/display-fallbacks.css` and the theme's own fallback stack from its manifest; the CMS string is only compared with the enum. That CSS is checked as a whole against `DISPLAY_FONT_RULE` (`server/utils/displayFonts.ts`: fixed grammar, no `<`, `{` or `;` inside a value) and left out, with a logged error, if it fails. The preload is a `<link>` in the same `render:html` hook. The files are served same-origin at `/fonts/display/` (woff2 and OFL texts only), always with the sandbox `Content-Security-Policy` of `/fonts/` (its route rule is set by the core, whether or not the theme has fonts) and cached for a year, since the URL carries `?v=<hash>`; so `font-src 'self'` is enough and the CSP does not change. **Provenance:** the five files are subset from OFL fonts of github.com/google/fonts at one pinned commit; `app/assets/fonts/display-sources.json` and `THIRD-PARTY.md` record the commit and the sha256 of each source TTF, license text and committed woff2, `test/displayFonts.test.ts` fails if a committed file changes, and `scripts/perf/subset-display-fonts.py` (dev-only, never run by the build) downloads from the pinned commit, verifies the input hashes before subsetting and reproduces the woff2 byte for byte. `style-src` already allows `'self' 'unsafe-inline'` (ADR 0004); the CSP plugin runs before `themeMode.ts` and hashes scripts only, so if `style-src` is tightened later this block needs a hash computed after it is pushed. The Strapi token needs no new permission: `site-setting.find` covers the nested `theme` populate, and `homePage` (populated with `slug` only, validated against the page slug pattern) needs the `page.find` the page routes already use. Every SSR render now awaits the cached site settings, so `siteCacheSeconds` must stay above 0 in production; with 0, each render (private pages included) makes a Strapi request with a 3 s timeout.
- **`/theme/images/`** is the active theme's `images/` copied into the build (`<buildDir>/micelio/public/theme/images/`) and served same-origin as static files; `/_ipx` (`<NuxtImg>`) reads the same copy. Only `png`, `jpg`, `jpeg`, `webp`, `avif`, `gif` and `svg` files are copied (others are skipped with a warning) and a symlink fails the build, so nothing outside the theme directory can be published. The static files carry `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; sandbox`, so an SVG opened directly runs no script and loads nothing; as an `<img>` or through `/_ipx` it renders as usual.
- **Theme messages** (`themes/<id>/i18n/*.json`) are trusted text from the repository. They are compiled at build like the core locales and rendered escaped by `t()` and `<i18n-t>`, never through `v-html`.
- **Startup check.** `runtimeConfigCheck` throws if the runtime `NUXT_PUBLIC_THEME` differs from the build, in production and in dev. In production, in server mode, it also warns (never fails) when `newsletter`, `comments` or `accounts` is on and the site's `privacyContactEmail` is empty; the warning is skipped when the site settings could not be loaded.
- **`/fonts/`** is the active theme's `woff`, `woff2` and `txt` (license) files, copied into the build (`<buildDir>/micelio/fonts/`) and served same-origin as static files. Any other file of `fonts/` (sources, scripts) is skipped with a warning, a symlink fails the build, and the files carry the same sandbox `Content-Security-Policy` as `/theme/images/`. The license texts stay at `/fonts/OFL-*.txt`. No CSP source is added.
- **`media-src`** (page sections, #244): `'self'` plus the same origins as `img-src` (Strapi and `NUXT_MEDIA_URL`), so the `<video>` of a section can play Strapi files and nothing else. Videos never autoplay (`controls muted playsinline preload="metadata"`).
- **Trust model.** A theme is installed by the operator, and its slots are Vue code that runs at build time and during server rendering, with the privileges of the app. The validator below is a **contract lint**: it catches mistakes and keeps themes inside the contract (hooks, layers, assets), but it does not sandbox code. The **CSP** (ADR 0004: `img-src`, `font-src`, `style-src`, `script-src` hashes) is the boundary for what a page can load in a visitor's browser. Install only themes you trust, as you would an npm dependency.
- **The contract validator** (`modules/theme/contract.ts`, `validate.ts`, `css-rules.ts`, `island.ts`, `files.ts`) runs at build on every installed theme, not only the active one, and fails the build naming the theme and the problem. It rejects theme ids that are not `[a-z0-9-]+` or differ from the folder, duplicate ids, unknown keys, font files that are not plain `.woff2` names or are missing, image roles that are not files of `images/`, token names and mode ids outside `[\w-]`, role values containing `; { } < > @ !`, a backslash, a backtick, `/*`, `url(`, `image-set(`, `src(` (and quotes, outside font stacks), and symlinks or files that resolve outside the theme folder for its stylesheets and slot components. The role CSS generated from `theme.json` goes through the same CSS checks as the theme's own stylesheets. Contrast and the static budgets are not checked by the build; `npm run theme:check` (and CI) runs them on top of this validator.
- **Theme CSS** (`theme.css`, `slots/*.css`, `fonts.css`, `font-fallbacks.css` and the local files they `@import`) is parsed with Lightning CSS and rejected for: a `myc-*` class or core `data-*` attribute that is not a public hook (`app/theme/hooks.json`; selectors are walked in every nested list, including `:is()`, `:not()`, `:has()`, `:host()`, `::slotted()` and `nth-child(… of …)`, and a `[class…="myc-…"]` selector is flagged; the old `bd-*` classes, `data-bd-*` attributes and `[class…="bd-…"]` selectors are rejected with a message that names the `myc-` replacement, for one release line, #422), `!important`, a remote `@import` or one that leaves the theme folder, and any `url()`, or string inside `image-set()` or `src()`, that is not a `/fonts/…` or `/theme/images/…` path (or a `#fragment`) without `..` segments or encoded dots, slashes or backslashes, in declarations, custom properties and `@property` initial values. This keeps what a theme's stylesheet asks the browser to load inside its own package, which is also what the CSP allows. Slot components (`slots/*.vue`) may not contain a `<style>` block (it would be bundled outside the `myc.theme` layer, and their CSS belongs in `slots/*.css`), and a slot that does not declare `island` is rejected for event handlers, `v-model`, object or dynamic `v-bind`, `onX` props, lifecycle hooks (composition and Options API), `useState`, `watch*`, timers and `addEventListener`. That last check is a lint over the slot's own file, not over what it imports; the slot's code is otherwise reviewed with the theme like any dependency.

## Dependencies

- CI fails on any **critical** `npm audit` finding (`npm audit --audit-level=critical`). Dependabot alerts and security updates are on; weekly update PRs come grouped. Major updates of Node and `@types/node` are ignored on purpose: the runtime is distroless Node 22, and moving to a new major is done by hand in both Docker stages and the CI.
- GitHub Actions are pinned by commit SHA.

### Remediation time frames

How long a vulnerable dependency may stay (ASVS V15.1.1 and V15.2.1). The clock starts when the advisory is published.

| Where the component runs | Critical and high | Medium and low |
| --- | --- | --- |
| In the production image or in the visitor's browser | 14 days (the same as a vulnerability in our own code, `SECURITY.md`) | The next planned release |
| Build and development tooling only | The next planned release | The next planned release |

## Static site publishing tokens

The workflow `.github/workflows/static-site.yml` ([operate/static-site.md](operate/static-site.md)) and the CMS rebuild hook hold two more credentials, none of them in the generated site:

- **Dispatch token** (`REBUILD_HOOK_TOKEN`, stored in the CMS environment): a fine-grained personal access token limited to the site's repository with **Contents: Read and write**, the minimum `POST /repos/{owner}/{repo}/dispatches` accepts. It can push code, so keep it only in the CMS, rotate it before it expires and never reuse it elsewhere. The payload carries content identifiers only.
- **Cloudflare token** (`CLOUDFLARE_API_TOKEN`, a GitHub secret): *Account, Cloudflare Pages, Edit* and nothing else (no DNS, no Workers, no zone permissions).
- **Build token** (`STRAPI_BUILD_TOKEN`, a GitHub secret): the CMS `build` token above, exposed as `NUXT_STRAPI_API_TOKEN` only in the generate step. The workflow has `contents: read` permissions and does not run for forks or when `STATIC_SITE_ENABLED` is not `true`.
- **Builder image** (`micelio-builder`, [operate/static-site.md](operate/static-site.md#builder-image)): the build token reaches it only as a run-time `NUXT_STRAPI_API_TOKEN` of the `generate` command, never as a build argument or in a layer; `.dockerignore` keeps `.env*`, keys and certificates out of the context. The image runs as uid 1000, and the token is not written to `/out` (the generated site holds no credentials). Pass it with an `--env-file` or a secret, not a committed compose file.

## Password rules

What a new password must satisfy (ASVS V6.1.2, V6.2.4, V6.2.11, V6.2.12). The frontend checks them on the server, before the CMS is called; the sign-up page repeats the context check in the browser so the message comes at once.

| Rule | Where it applies | Notes |
| --- | --- | --- |
| At least 10 characters and at most 72 bytes | Sign up, reset, change | `isValidPassword` in `app/helpers/auth.ts`, shared with the forms. 72 bytes (UTF-8: an accented letter counts two, an emoji four) is what the CMS can hash; a longer one is refused with its own message. There is no composition rule (no required digit or symbol) |
| Not built from the context | Sign up, change | The password must not contain the username, the address before the `@` or the parts of either, or the name of the site (in each language), ignoring case, accents and separators. Words shorter than four characters are not counted (`app/helpers/passwordContext.ts`). The error is `weakPassword` |
| Not one of the 3000 most common | Sign up, reset, change | A new password that equals one of the 3000 most common passwords of at least 10 characters, ignoring case, is refused with `commonPassword` (`server/lib/commonPasswords.ts`; the list is from SecLists, see `THIRD-PARTY.md`, and is rebuilt with `scripts/common-passwords.mjs`) |

What is not checked, and why:

- **The context words at reset, in the frontend.** The reset route receives a code and a password, not the account, so it cannot know the username or the address; the CMS can, and it checks them for readers (micelio-cms#177, ASVS V6.2.11). The change route knows the account (it reads the person's profile first) and applies both checks.
- **Breached password sets (ASVS V6.2.12), accepted risk.** Beyond the list above, a password is not compared with the large sets of leaked passwords. Doing it means asking a third-party service (even by hash prefix) or shipping a set of hundreds of millions of entries; the first breaks the rule that the site makes no request to a third party (standard, section 9), and the second is out of proportion for accounts that only comment and subscribe. Length (10 or more, and the interface suggests a long phrase) and the list of common passwords are the compensation. Revisit it if the accounts hold more than an email and a username.

## Logs

The server writes one JSON object per line to the standard error through `logError` and `logWarn` (`server/utils/log.ts`); it keeps no log file and sends logs nowhere else, so the destination is whatever the operator's platform does with the container's output (ASVS V16.2.3). A test fails when a server file writes to `console` directly.

A line has `time` (UTC, ISO 8601), `level` (`info`, `warn` or `error`), `event` (a stable dotted name such as `cms.search`), `message` (fixed text) and, when it comes from a request, `route`, `requestId` and `visitor`; `cause` holds what went wrong, as `upstreamLogMessage` says it (V16.2.1, V16.2.4). `requestId` is a random id drawn per request, never read from a header; each internal `/api` call of a page render is its own request. A line written outside a request, or by a helper that receives none (boot checks, site settings, page sections, theme), has no `route`, `requestId` or `visitor`. `visitor` is the first 12 hex characters of an HMAC-SHA256 of the visitor's address with a key drawn at random when the process starts: it groups one visitor's lines without holding the address, and it changes on a restart and is not shared between instances.

What a log line may hold (standard, section 4: no secrets, email addresses or raw IP addresses):

- **A failed call to the CMS** is logged with `upstreamLogMessage(error)` (`server/utils/upstreamError.ts`): the status and the message the CMS sent, never the request URL, because the URL of a lookup holds a reader's email address or a token in its query (V16.2.5). An error of our own code keeps its name and message; one with a `code` (a mail or network error) keeps only the name and the code, because its message can hold the address it failed on.
- **A value from the CMS or a visitor** that is written into a message goes through `logText()`: control characters, line breaks included, become spaces and the text is cut at 300 characters, so a value cannot start a forged line (V16.4.1). `upstreamLogMessage` does it itself, and so does the theme log.
- A unit test (`test/noRawErrorLogs.test.ts`) fails when a server file passes a caught error to `console` as it is.

### Security events

These events are written on purpose (ASVS V16.3.1, V16.3.2, V16.3.3). Each line also has the route, a request id and the hashed visitor described above, so the route says which form or endpoint it was. `cause` is a fixed word, never something the visitor typed: no password, identifier, email address, token, `Origin` value or query.

| `event` | Level | When | `cause` |
| --- | --- | --- | --- |
| `auth.login.success` | `info` | A sign-in worked | |
| `auth.register.success` | `info` | An account was created | |
| `auth.password-reset.success`, `auth.password-change.success` | `info` | A password was reset or changed | |
| `auth.account-delete.success`, `auth.logout` | `info` | An account was deleted, a visitor signed out | |
| `auth.confirm-email.success` | `info` | The CMS confirmed the email address | |
| `auth.forgot-password.requested`, `auth.resend-confirmation.requested` | `info` | The CMS accepted the request (the answer to the visitor is the same whether the address exists or not) | |
| `auth.failure` | `warn` | An auth call was refused: wrong credentials, unconfirmed email, weak or common password, no session, the CMS's own rate limit | The auth error code (`invalidCredentials`, `emailNotConfirmed`, `weakPassword`, `unauthorized`, `tooManyRequests`…) |
| `authz.origin-refused` | `warn` | A state-changing request came from another origin or without an `Origin` | |
| `authz.draft-refused` | `warn` | A draft request had no session, or the CMS refused the editor session (401 or 403) | `noSession` or `upstream 401`/`upstream 403` |
| `limit.rate` | `warn` | The site's own rate limit refused a request | The bucket (`commentPerIp`, `newsletterPerEmail`…) |
| `input.refused` | `warn` | A body or a query was refused by its schema, a payload was too large, or a newsletter confirmation or unsubscribe token was missing or unknown (repeated guessing shows here) | The names of the refused fields, `payloadTooLarge`, `missingToken` or `invalidToken` |
| `analytics.proxy` | `error` | The call to Umami through the first-party proxy failed (no answer, or a redirect, which becomes a 502) | `upstream 502`, with the name and code of the failure behind it when there is one (a socket or TLS error) |
| `server.unhandled` | `error` | An error nobody handled reached Nitro: a bug in a request, an error raised outside one, or a crash (`uncaughtException`, `unhandledRejection`) | The error's name and code, never its message |

A flood of refused requests writes a line per request: the platform that collects the logs decides how long they are kept and whether to sample them.

Not logged: a malformed path parameter or a malformed `relation` or `documentIds` value, which scanners produce in volume and which reach no control. For a page, Nitro still writes its own report of an unhandled error, as free text over several lines with the request URL and its query; for `/api/*` the problem details plugin (`server/plugins/problemDetails.ts`) answers the error itself and only the structured `server.unhandled` line is written. The format, the destination and the retention in one place: [operate/logging.md](operate/logging.md).
